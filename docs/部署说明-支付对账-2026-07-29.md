## 本批解决什么

2026-07-28 掉单事故的根因已定位：

```
15:20:33      创建订单 PROD20260728072033017383
15:21:02.656  第1次调 wechatPay → 商户单号 A = PROD178522326265673 → 写库
15:21:04.252  1.6秒后第2次调 wechatPay → 单号 B = PROD1785223264252216 → 覆盖 A
15:21:09      用户在第1个支付面板完成付款，微信按 A 扣款
              回调携 A 返回 → 库中已是 B → 查无此单 → 静默 return
              订单永久停在 pending，核销码未生成
```

本批做三件事：
1. **回调按历史单号反查** —— 当场闭环，同类问题不再发生
2. **定时对账补单** —— 兜底网，任何原因导致的掉单最多存活 10 分钟
3. **异常落库留痕** —— 日志只存 30 天且可能被关闭，资金链路失败必须落库

## ⚠️ 开始前的两件准备

### 准备 1 · 手工创建 `pay_exceptions` 集合

云开发控制台 → 数据库 → 集合名称旁 `+` → 新建 `pay_exceptions`

**不建的后果**：云开发 `add()` 不会自动创建集合，会报 `-502005`。代码用 try/catch 包住了，主流程不受影响，但**所有异常留痕静默丢失**，本批次的核心目的（可追溯）完全落空。

> 本项目已有先例：`admin_logs` 当初就是因为集合未建而报错。

### 准备 2 · 首次部署前先删掉定时器

编辑 `cloudfunctions/reconcilePayment/config.json`，把 `triggers` 整段删掉。

**原因**：这是生产售票系统，`queryOrder` 的实际返回结构尚未实测验证过，先手动单笔确认再放开全量扫描。验证通过后（步骤 4）再加回来。

> 云函数超时**不在这一步**——那个必须部署之后才能在控制台配置，见步骤 2。

## 部署与验证（严格按顺序，不要跳步）

### 步骤 1 · 部署 `reconcilePayment`

微信开发者工具 → 右键 `cloudfunctions/reconcilePayment` → **上传并部署：云端安装依赖**

此时它没有定时器，不会自动跑，纯待命状态。

### 步骤 2 · 部署完成后，去控制台把超时改为 60 秒

云开发控制台 → 云函数 → `reconcilePayment` → 配置 → 超时时间 → **60 秒**

**为什么必须在部署之后**：函数不存在时，控制台里没有这一项可配。

**为什么必须手工改**：云函数默认超时仅 **3 秒**，且 `config.json` 只支持 `triggers/name/type/config` 四个字段，**没有 timeout 字段**（[官方文档](https://developers.weixin.qq.com/miniprogram/dev/wxcloud/guide/functions/triggers.html)），无法通过代码配置。

**不改的后果**：函数在 3 秒被杀。不会写坏数据（`markPaid` 是单条原子更新），但基本补不了单。

> ⚠️ **待验证**：重新上传代码是否会重置该配置，尚未实测。保险起见，**每次重新部署 `reconcilePayment` 后都回来确认一次超时仍是 60 秒**。

### 步骤 3 · 手动验证（见下方「验证流程」第 1、2 步）

确认 `queryOrder` 能正常调通、参数和返回解析都对。

### 步骤 4 · 加回定时器，重新部署 `reconcilePayment`

把准备 2 删掉的 `triggers` 段恢复，重新上传部署，然后**回步骤 2 复查超时设置**。

至此**兜底网已上线**：此后任何原因导致的掉单，最长 10 分钟自动修复。

### 步骤 5 · 部署 `wechatPayCallback`

风险中等（改了回调核心逻辑），但新版本对新旧订单都兼容。

### 步骤 6 · 部署 `wechatPay`

### 步骤 7 · 用 0.01 元真实支付验证（见「验证流程」第 3 步）

这一步确认云函数改动没有破坏当前正常工作的支付流程。**通过后云端就稳了。**

## 验证流程

### 第 1 步 · 只读验证 `queryOrder` 能跑通

`reconcilePayment` → 云端测试，参数：

```json
{"orderNo":"PROD20260728072033017383"}
```

**预期**：返回 `result: "not_paid"`，`states` 里能看到微信对单号 `PROD1785223264252216` 的真实回应（应为 `NOTPAY`）。

- 若返回 `NOTPAY` → **`queryOrder` 调用正常**，参数命名和返回解析都对
- 若报错 → 把错误贴出来，多半是入参命名（驼峰 vs 下划线）问题

> 注意：这笔事故单**不会被自动补回来**。它的 `outTradeNoHistory` 字段不存在（该字段是本批新增的），库里只有被覆盖后的单号 B，而 B 从未被支付。**这一笔必须手工补**，见下方附录。

### 第 2 步 · 全量扫描（仍不开定时器）

参数留空：

```json
{}
```

看返回的 `scanned` / `processed` / `repaired`：

- `repaired` 大于 0 → 有其他掉单被自动修复，记下订单号
- `repaired` = 0 → 说明只有 7-28 那一笔，属偶发

### 第 3 步 · 验证回调没被改坏

用 **0.01 元**真实下单支付一次（游船或商品均可），确认：

- [ ] 支付后订单正常变为 `paid`（或商品无需核销时为 `completed`）
- [ ] 核销码正常生成
- [ ] `pay_exceptions` 集合里**没有**新增记录（正常流程不应留痕）

这一步是确认 `wechatPayCallback` / `wechatPay` 的改动没有破坏当前正常工作的支付流程。

对应上方部署步骤 7。定时器的开启在部署步骤 4，此处不再重复。

## 上线后观察

定期翻 `pay_exceptions` 集合，按 `type` 判断：

| `type` | 含义 | 处理 |
|---|---|---|
| `order_not_found` | 商户单号对不上 | 小程序新版发布后应归零；若仍出现，说明还有未知的重复下单路径 |
| `callback_on_abnormal_status` | **钱已收但订单已取消/退款** | **人工介入**，核实退款或补发 |
| `callback_duplicate` | 订单已被补单任务处理 | 正常，说明兜底网在工作 |
| `callback_not_success` | 回调返回非成功状态 | 看 `rawEvent` 排查字段解析 |
| `order_repaired` | 补单成功 | 正常，但要看频次 |

## 本批未解决的问题

根因已在 `4b51b97` / `4781bcb` 修复（重入锁、加载提示、单号复用、关单换号重试），
但**前端部分要等小程序审核通过才生效**，在此之前云端兜底网是唯一防线。

审查中维持 🟠、本批未处理的：

- 同一订单被**扣款两次**时只处理第一笔（需人工介入，非自动止损）
- 补单和回调两条路径均**无金额校验**
- `orders` 集合缺 `status` + `createdAt` 组合索引
- 无 pending 订单自动关单机制（微信侧关单后靠 `wechatPay` 换新单号兜住，但订单会一直堆在库里）

更大范围的问题（鉴权漏洞、微信押金未退等）见 `工作清单-2026-07-29.md`。

## 附录 · 修复 7-28 事故单

改动前**先点「导出」备份该条记录**。

orderNo == PROD20260728072033017383

### 方案 A · 改一个字段后让补单函数自动修（推荐，需先完成部署步骤 1-2）

给记录补上历史单号字段，把真实被扣款的那个单号填进去：

| 字段 | 值 |
|---|---|
| `payment.outTradeNoHistory` | `["PROD178522326265673"]`（数组类型） |

然后云端测试 `reconcilePayment`：

```json
{"orderNo":"PROD20260728072033017383"}
```

补单函数会拿这个单号去问微信，确认已支付后自动写入 `status`、`verificationCode`、
真实的 `transactionId` 和 `paidAt`，数据完整性比手改好。

**附加价值**：这是用一笔**真实已支付订单**验证补单函数的机会，
比只跑 `not_paid` 分支的验证有价值得多。若返回 `repaired`，说明整条链路真的通了。

### 方案 B · 纯手工改字段（部署前也能做，游客等不及时用这个）

| 字段 | 改为 | 必要性 |
|---|---|---|
| `status` | `paid` | 必须 |
| `verificationCode` | 6 位大写字母数字，不含易混淆的 I/O | 必须 |
| `payment.outTradeNo` | `PROD178522326265673` | 建议（对账准确性） |
| `payment.transactionId` | `4500000287202607283553778448` | 建议（对账准确性） |

> 若已用方案 B 手工补过，订单状态已不是 `pending`，方案 A 就跑不了了
> （`reconcilePayment` 只处理 `pending` 订单，会直接返回"无需补单"）。**两者二选一。**
